## Обсяг у межах процесу 1000475

Будуємо тільки **клієнтську частину** — подачу заяви у ЦНАПі («Портал Дія», виконавець — Адміністратор ЦНАПу): форма 5 кроків, генерація й підпис заяви, виклик зовнішнього сервісу «Створення заяви…», статуси/повідомлення.

**Поза межами**: БП «Опрацювання запиту на формування витягу з Реєстру ветеранів» (виконується на боці ПЗ Реєстр/КУО), самі реєстри «Журнал запитів» і «Реєстр сформованих витягів» — вони на боці зовнішньої системи, тут потрібні лише як контракт даних для інтеграції.

Усього атомарних вимог: **41** (R0.1–R8.3), з них до реалізації в 1000475: **35** (Групи 0–7), інформативних/поза межами: 3 (Група 8).

## Відкриті питання перед стартом

Дивись `requirements-edrvv.md` → розділ «Відкриті питання». Жодне з них не блокує старт розробки форми — усі стосуються деталей зовнішньої інтеграції (номери реєстрів, метод QR, параметри запиту ДРАЦС), які власник ТЗ уточнить окремо. Розробка йде за дефолтами/ASSUMPTION, позначеними в таблиці вимог.

## Порядок реалізації (групами по зв'язності, структурне → залежна логіка → інтеграції/PDF)

### Група А — Каркас процесу (R0.1, R0.2)
- Перейменувати `workflow 1000475` під послугу, прибрати тестовий task.
- Побудувати базовий маршрут кроків: Start → Крок1 → Крок2 → Крок3 → (умовно) Крок4 → Крок5 → підпис → виклик сервісу → очікування відповіді → статус/повідомлення → End.
- `liquio-research` — за потреби звірити з референсними прецедентами подібних послуг ЦНАП на цьому інстансі.

### Група B — Крок 1 (R1.1)
- Підказка з дослівним текстом (`literal-edrvv.md`).

### Група C — Крок 2 «Хто подає заяву» (R2.1–R2.11, включно з довідником R2.8)
- Радіокнопка вибору заявника + вся умовна логіка показу/обов'язковості блоків.
- Довідник «Документи надані законним представником» (13 записів, Додаток 1) — окремий реєстр-довідник.
- Сніпет дати (R2.5) — переносити той самий патерн 4 рази в межах кроку.
- Найбільша структурна складність кроку — робити однією зв'язною групою, `liquio-snippets` для дати, `liquio-rules` перед вибором типу довідника.

### Група D — Крок 3 «Відомості про заявника» (R3.1–R3.7)
- Увесь блок — стандартні сніпети (`liquio-snippets`): ПІБ, РНОКПП/паспорт, телефон, email.
- Умовні поля: РНОКПП обов'язковий лише для «Ветеран/член сім'ї загиблого», дата народження — лише для «Дитина».

### Група E — Крок 4 «Відомості про ветерана» (R4.1–R4.2)
- Показ кроку за умовою типу заявника.
- Повторне використання тих самих сніпетів, що й у Групі D (без телефону/email/дати народження).

### Група F — Крок 5, PDF-шаблони, фінал (R0.3, R0.4, R0.5, R5.1–R5.3)
- Генерація заяви PDF на кожному кроці (стиль Дії, всі поля форми) + підпис поточного користувача + цикл «перевірка → редагування».
- 5 варіантів фінального PDF-витягу (наявні статуси / для дитини / по померлій особі / уточнення / відсутність даних), QR-код, КЕП Мінветеранів.
- Обов'язково `liquio-pdf` — і для заяви, і для кожного з 5 варіантів витягу.

### Група G — Статуси та повідомлення (R6.1–R6.5)
- 5 подій/статусів з дослівними текстами (`literal-edrvv.md`), кабінет + пошта, вкладення PDF де потрібно.

### Група H — Інтеграція (R7.1–R7.4)
- Виклик сервісу «Створення заяви на формування витягу з ЄДРВВ» з повним payload, `source=portalDiiaCnap`, блок `cnapAdministrator`.
- Обробка помилки `{error:{message, traceId}}` → маппінг на статус «СТАЛАСЯ ПОМИЛКА».

### Фінал — Група I: `liquio-validate` (повний цикл)
- Input'и, вкладеність умов, дослівні тексти (literal diff), BPMN-маршрут, інтеграція, усі 5 PDF-шаблонів, регресія.
- Викликається розробником явно перед здачею.

## Ризики, що потребують підвищеної уваги

- **R2.7 / R2.8** — комбінація довідника + умовної розширеної версії списку («+ Довіреність» лише для одного типу заявника) — легко переплутати умову видимості.
- **R5.3** — 5 окремих PDF-шаблонів з різним вмістом і QR — найбільший обсяг роботи в проєкті, закладати найбільше часу.
- **R7.1** — великий вкладений payload (до 4 рівнів вкладеності) — звіряти з JSON Schema сервісу перед реалізацією, не «на око».
- **Група 8 (R8.1–R8.3)** — відкриті технічні деталі зовнішньої системи; тримати в `NEEDS_DECISION`, не блокувати ними інші групи.
